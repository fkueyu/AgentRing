# 架构决策

[中文](decisions.zh.md) · [English](decisions.md)

小型的本地工具：优先选最简单的设计，让灯环保持响应、API 接口保持无聊。这些记录写下
那些否则会被反复重提的决策。

## ADR-001: 守护进程与菜单栏 App 之间保留 HTTP 轮询

**状态：**已接受，2026-11-24。

即使预览窗口关闭，App 也需要菜单栏计数。目前它每 1.5 s 轮询 `/state`、每 3 s 轮询
`/health`；预览只在可见时以 30 fps 拉取 `/frame`。

| 方案 | 取舍 |
|---|---|
| 轮询（当前） | 无状态、容易恢复、服务端没有长驻状态；状态延迟最多 1.5 s |
| Server-Sent Events | 延迟更低、请求更少；但需要重连/退避、事件 ID 和 App 侧的长任务 |
| WebSocket | 对单向状态流来说，双向能力属于过度设计 |

**决定：**暂时保留轮询。真正重要的状态变化（等待、报错）在实体灯环上同样可见，而
1.5 s 远短于一个人注意到菜单栏变化所需的时间。如果延迟成为明确需求、App 跑在对电量
敏感的机器上，或者多个客户端让轮询开销变得可测量，再重新考虑。

## ADR-003: 守护进程是唯一的渲染器和唯一的动效目录

**状态：**已接受，2026-11-24。

`renderFrame` 是唯一的视觉契约：App 预览通过 `/frame` 读取，ESP32 通过 TCP 帧流读取
同样的 72 字节。动效 ID、标签和默认值都在 `daemon/src/effects.mjs`；App 从
`GET /capabilities` 拉取，不再维护第二份选择器/标签表。

**取舍：**App 保留少量离线兜底，守护进程下线时设置仍能渲染；离线时新增动效没有意义。
渲染器的 switch 仍需为每个动效写一条分支，但配置校验和 UI 选项来自同一份目录。

## ADR-004: 控制面只监听 loopback

**状态：**已接受，2026-11-24。

局域网只能访问 `/frame`、`/health` 和只读的 7802 帧流（ESP32 需要它们）。预览、
`/state`、`/config`、`/config/reset` 和所有写操作只接受 loopback。`/state` 含
当前工作目录（cwd）路径，暴露到局域网既有隐私问题，也平白多出攻击面。

**取舍：**从另一台机器用浏览器预览不再可用。以后如果确实需要远程预览，新增只读、
脱敏的 `/public/state`，而不是开放现有接口。

## ADR-005: 用持久原始 TCP 连接推送帧

**状态：**已接受，2026-11-24。

灯环只需要一路只读的视觉数据。与其每帧发一次 HTTP 请求，守护进程监听 TCP 7802，每个
33 ms tick 向所有已连接客户端写一帧 72 字节。固件保持一个 `WiFiClient` 打开，按
72 字节整帧读取；短读会断开 socket，触发重新解析/重连。渲染器和预览仍在守护进程里，
所以 `/frame` 和帧流共享同一份 `renderFrame` 结果。

**实测：**帧流约 29–30 fps，HTTP 轮询约 22–23 fps。

**稳健性：**固件保留 2 s 的帧流读超时（系统负载可能短暂拖住 Node 定时器），并按
`FRAME_INTERVAL_MS` 控制 LED 刷新节奏；缓冲区里的旧帧会被丢弃，只保留最新一帧。本地
帧流客户端不计入 `/health` 的局域网计数。

**取舍：**防火墙要再放行一个局域网端口；协议没有逐帧纠错（TCP 连接掉了就重连）；
App 必须读 `/health` 里的 `streamFrames`/`streamLastFrameAt`，旧固件则退回
`lanFrames`。App 预览继续走 `/frame`，本地 30 fps 路径保持独立。

## ADR-006: 待机动效与颜色是两个独立维度

**状态：**已接受，2026-11-24。

`orbit` 和 `rainbow` 原本是两个待机模式，却渲染出完全相同的彗星状光点，只有颜色
不同。这迫使用户把同一种动效选两遍，渲染器里也多留了一条重复分支。现在待机是动效
（`dot` / `orbit` / `breathe`）× 配色（`mono` / `rainbow` / `aurora` / `ember`）。
只有 `mono` 提供颜色选择器；其他配色是预设好的方案，颜色选择器不会和预设打架。

**取舍：**本 ADR 有意让运行状态沿用各自的 `colorMode`（solid/gradient/rainbow），
于是 App 有两套颜色词汇：一套给空闲灯环，一套给活跃会话。
[ADR-008](#adr-008-一套配色词汇配色是值不是宏) 把两者合并成一份目录，两个选择器现在
说同一种语言。`standby: "rainbow"` 的配置会迁移为 `orbit` +
`standbyPalette: "rainbow"`，已有安装看上去不变。

## ADR-007: 动效预览使用合成的 loopback 帧

**状态：**已接受，2026-11-24。

动效页需要展示当前并不在灯环上的动效。App 有意不在本地渲染它们：
`/preview?state=&effect=` 会构造一个单 agent 的合成快照，跑同一个 `renderFrame`，
返回常规的 72 字节帧。它不碰实时快照，也不碰实体灯环的帧流；App 把左侧预览栏指向该
URL，直到用户返回实时。

**取舍：**多了一个 loopback 路由；动效页预览时会多一条取帧循环。换来的是动效预览不会
和硬件渲染器产生偏差，预览也永远不会改变真实灯环显示的内容。

**部分被 ADR-010（2026-11-25）取代：**现在按请求会把预览镜像到实体灯环一小段时间
（TTL）；`GET /preview` 仍是这里描述的一次性取帧。

## ADR-008: 一套配色词汇；配色是值，不是宏

**状态：**已接受，2026-11-25。取代 v2 主题模型中的颜色部分。

v2 有四套互相重叠的颜色系统：主题预设（来源色 + 颜色模式 + 渐变目标）、颜色模式
（solid/gradient/rainbow）、纯色来源（state/source），以及自带一套词汇的待机配色。
只有部分组合能真正到 LED 上——选单色 / 按状态时，选薄荷不会看到任何可见变化。另外
两个 bug 把剩下的也藏住了：渲染器把单个十六进制字符串传给 `colorFor`，而它期望的是
一个 map，于是**所有自定义来源色都被忽略**；App 动效页在灯环按来源或预设取色时，仍
显示状态色圆点。配色页最后变成了五个主题块、三个模式块、一个双向的状态/来源开关、
六个状态色块和十八行来源。

**决定：**用一个 `display.accent` 值从单一配色目录里选出运行中的颜色；空闲灯环也从
同一份目录里选（`mono` + 预设渐变 + `rainbow`）。`state` 和 `source` 是身份配色；
`neon` / `sunset` / `mint` / `aurora` / `ember` 是预设渐变，色标沿灯环分布；
`rainbow` 是漂移的色轮。等待 / 完成 / 报错始终保留各自的 `stateColors` 条目。配色是
值：选择某个配色不会改写其他字段。主题、`colorMode`、`gradientTo`、`solidColorBy` 和
`motion.tempo` 已移除，v2 配置按“当时看到的颜色”迁移（见
[配置与 API](configuration.zh.md#迁移到-v3)）。

App 的灯光分区从五个变成四个。颜色和动效现在共用**状态**分区：一个会话配色选择器，
只显示渲染器真正会读的颜色块；然后每个状态一行，配它的动效和速度；最后是来源列表。
左侧栏汇总会话配色和提醒色。

**取舍：**

- “状态色渐变到指定第二颜色”的外观没有了。预设渐变提供渐变效果；身份配色保持纯色，
  这正是它们在 6 颗灯珠的弧段上可读的原因。带自定义主题的 v2 渐变会迁移成纯色身份
  配色。
- 渲染器按灯珠解析会话配色，需要分段索引，所以 `lightFor` 接收
  `(segment, segments)`。在 24 颗灯珠 / 30 fps 下可以忽略。
- `stateColors` 和 `sources` 仍是 map，但对应的色块只在用到的地方显示：状态配色显示
  六个色块，预设渐变显示三个提醒色块，来源卡片下显示按来源的色块（由来源色配色启用）。
- 多了一个仅开发用的 App 钩子（`AGENTRING_BASE`），让截图可以跑在测试用的守护进程上，
  而不是实时灯环。

## ADR-009: 从 manifest 判断 agent 接入，而不是跑 CLI

**状态：**已接受，2026-11-25。

来源页需要说明某个 agent 工具及其 AgentRing 接入是否装好。三个方案：

| 方案 | 取舍 |
|---|---|
| 跑每个工具的 CLI（`dsh plugin list`，……） | 权威，但慢，可能初始化 profile 或卡住，输出也不是稳定的 API |
| 读每个工具自己的 manifest（采用） | 便宜、离线、不挑版本；但属于启发式，准确度取决于我们知道哪些文件 |
| 只看流量推断 | 能证明接入可用，但第一个会话之前什么都显示不出来，也无法解释缺了什么 |

**决定：**在 `daemon/src/sources.mjs` 里维护一组文件系统探测，每个 agent 一个，由只
接受 loopback 的 `GET /sources` 提供。探测会报告是否安装（app bundle / 数据目录 /
CLI）、接入状态（`installed`、`missing`、`disabled`、`mismatch`、`manual`）、
`installable`，以及确切的命令。运行中的 DSH profile 从桌面宿主进程参数解析，所以装在
别的 profile 里的插件会显示为可见的“不匹配”，而不是假的成功。

App 每 10 s 重新读取报告。对 Codex 和 Claude，`installable` 为 true，
`POST /sources/<id>/install` 会执行 AgentRing 自己的安装脚本；脚本会合并进工具的配置，
保留别人的 hook，备份原文件，并且可重复执行。只有 `BRIDGE_INSTALLERS` 里的脚本可执行：
探测给出的展示命令（DSH 的包管理命令）只能复制，所以这个接口永远无法被用来跑任意命令。
活动状态有意不放进响应；页面把 `/sources` 和 `/state` 里的会话合并起来。

**取舍：**被 loader patch 行禁用的 bundle 对探测不可见（只检查 profile 的 bundle
列表）；外部改动最多滞后一个轮询周期；装好的 hook 仍需工具自己的一次性信任确认才会
触发。新增一个 agent 需要写探测（如果支持一键接入还要写安装器），而不是只调一次
`/ingest`；`/ingest` 仍是通用契约，探测只负责解释接入情况。

## ADR-010: 动效预览带 TTL 镜像到实体灯环

**状态：**已接受，2026-11-25。

只在屏幕上试听动效不够：用户希望挑动效时实体灯环显示同一个合成帧。于是 App 让守护
进程持有一个临时的预览覆盖：`POST /preview {state, effect, ttlMs}`。覆盖生效期间，
`/frame`、浏览器预览和原始 TCP 帧流都返回合成帧；`DELETE /preview` 恢复实时快照。
预览打开时 App 会续 TTL（默认 45 s，心跳 15 s），预览关闭、切分区或窗口消失时清除。
过期的覆盖会退回实时，所以崩溃的客户端无法把灯环钉住。

**取舍：**试听期间灯环不再显示实时会话（App 有标注）；任何 loopback 客户端都能改灯环
显示的内容（本机只有一个用户）；帧源每个 tick 检查一次过期。预览仍走常规渲染器，所以
伽马、电流上限和夜间模式与实时状态完全一样生效。
